# Spec proposal: Operational models, `$context`, and related grammar

**Status:** Draft proposal (not yet applied to the spec pages)
**Branch:** `spec-operational-models`
**Origin:** Provenance work in `FHIRconnect-mapping-lib`
(`model/operational/provenance/`, see its `provenance-decisions.md` arc42 ADRs).

## Motivation

FHIRconnect model mappings today connect a FHIR resource to **one openEHR
archetype** (`openEhrConfig.archetype`), driven by composition data and
bidirectional by default. Provenance broke every one of those assumptions:

- It describes the **transformation itself** (what was produced, from what,
  when, by whom), not clinical content — so it has **no archetype**.
- It is **generated by the engine as a side-effect** of a run, not requested.
- It is **generate-only** (openEHR→FHIR); you never rebuild a composition from a
  Provenance.
- A few values come from **outside** the composition (the participant/`who`).

This proposal introduces the minimal grammar to express that class of mapping,
keeping ordinary archetype mappings unchanged.

---

## 1. Operational models (new `type`)

**Page:** `types-of-mapping-files/model-mappings.adoc` (add a section) or a new
`types-of-mapping-files/operational-mappings.adoc`.

A model mapping with **no `openEhrConfig`** that the engine emits as a
side-effect of a run. Its fields come from four sources:

- **Engine** — run-intrinsic, not expressible in YAML (`target[]`, `id`,
  `recorded`, list iteration, engine-built values).
- **Defaulted** — `manual` literals in the YAML.
- **Context** — optional per-call input (see §2).
- **Composition** — ordinary openEHR paths, where applicable.

Worked example: `Provenance` in the mapping library
(`model/operational/provenance/provenance.yml`).

Header difference from an archetype model:

```yaml
type: model
metadata:
  name: provenance
spec:
  system: FHIR
  version: R4
  fhirConfig:
    structureDefinition: http://hl7.org/fhir/StructureDefinition/Provenance
  # NOTE: no openEhrConfig — not derived from an archetype
```

**Open:** whether to keep `type: model` (distinguished by the missing
`openEhrConfig`) or introduce `type: operational`. Recommendation: keep
`type: model`; the absent `openEhrConfig` is the signal.

## 2. `$context` variable

**Page:** `basics/Variables.adoc` — add a row and a section.

`$context` is data passed into a mapping **from the REST call** (per-call). New
table row:

| Variable | Description |
|---|---|
| `$context` | Values supplied by the caller on the REST request (operational models only, for now) |

Rules:
- **Operational-models-only** for now (avoids authors routing source data
  through context in ordinary archetype mappings).
- **Per-call**: there is no "set once" config tier; a referenced context field is
  part of the request payload.
- **Source-derivable data must still come from the source** — context is only for
  values genuinely absent from the composition.
- **Closed key set** declared per engine deployment (not a free-form bag).

### 2a. `$context.*` inside `manual` values

**Page:** `types-of-mappings/concept-type/manual.adoc`.

Rather than a first-class `context:` source (parallel to `fhir:`/`openehr:`),
allow a `manual` `value:` to reference `$context.*`. `manual` is already the
openEHR-free channel, so the FHIR↔openEHR roundtrip is untouched; the only new
capability is a dynamic (vs literal) value.

```yaml
- name: "agentWhoContext"
  extension: "add"
  with:
    fhir: "$resource.agent.who"
  manual:
    - name: "who"
      fhir:
        - path: "$fhirRoot"
          value: "$context.who"   # dynamic value from the REST call
```

(Example: `provenance/examples/provenance_who_context.yml`.)

**Open:** promote to a first-class `context:` source only if context later needs
conditions, references, or roundtrip behavior.

## 3. `operational:` key in context files

**Page:** `types-of-mapping-files/context-mappings.adoc`.

A context **triggers** an operational model by listing it under a new
`operational:` key (a generation root, parallel to `archetypes:`), resolved by
`metadata.name`:

```yaml
context:
  profile: { ... }
  template: { ... }
  archetypes: [ ... ]
  extensions: [ ... ]
  start: "..."
  operational:
    - provenance      # emit a Provenance for this run
```

Rationale: Provenance is run-scoped, has no archetype, and is not a fragment of
another resource — so it fits neither `archetypes:` nor `extensions:`. Trigger
(`operational:`) and extend (`extensions:`) stay separate concerns.

---

## 4. Extending an operational model via `extends:`

**Page:** `types-of-mapping-files/extension-mappings.adoc`.

A `type: extension` may `extends:` an operational model **by its
`metadata.name`** (today `extends:` always names an archetype):

```yaml
type: extension
metadata: { name: provenance_who_context }
spec:
  ...
  extends: provenance    # operational model by name, not an archetype
```

This is where deferred/vendor/deployment-specific fields live (policy variants,
`agent.onBehalfOf`/institution, `who` override), listed under the context's
`extensions:`.

**Open:** confirm the resolution scheme for `extends:` naming an operational
model rather than an archetype.

---

## 5. Model-level `unidirectional`

**Page:** `model-mappings.adoc` (header) / wherever `unidirectional` is defined.

`unidirectional` is currently a **per-rule** field (`"openehr->fhir"` /
`"fhir->openehr"`). Operational models are generate-only, so allow declaring it
**once at model level** instead of repeating it on every rule:

```yaml
spec:
  system: FHIR
  version: R4
  unidirectional: "openehr->fhir"   # whole model is generate-only
```

Recommendation: operational models default to `openehr->fhir`; the explicit
model-level declaration documents it.

## Summary of grammar additions

| Addition | Scope | Page |
|---|---|---|
| Model mapping without `openEhrConfig` (operational) | new | model-mappings / operational-mappings |
| `$context` variable | new | Variables |
| `$context.*` referenced from `manual` value | new | manual |
| `operational:` context key | new | context-mappings |
| `extends:` an operational model by name | extends existing | extension-mappings |
| `unidirectional` at model level | extends existing | model-mappings |

## Open items (carried from the provenance work)

- `type: model` (no `openEhrConfig`) vs a dedicated `type: operational`.
- `extends:`/`operational:` resolution by `metadata.name` for non-archetype models.
- Canonical openEHR ObjectLocation NamingSystem URI (mapping-lib placeholder).
- Engine convention for writing a literal into a list field (`policy[0]` vs the list).
